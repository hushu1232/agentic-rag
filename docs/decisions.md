# 决策记录（ADR-lite）

> 每条只写四件事：问题、选项、裁定、理由。**被推翻的裁定不要删，标 `SUPERSEDED` 并指向新的。**
> 这份文件的作用：三个月后回来看「为什么当初这么定」，答案不靠回忆。

---

## ADR-001 · 语料自造，不用现成文本 — **SUPERSEDED by ADR-014**
**问题**：评测集要凑出「真需要两次检索」的多跳题和「语料确实没有」的无答案题，语料来源决定可行性。
**选项**：A 自造 28 篇虚构产品手册 / B 沿用天龙八部 / C 公开文档快照。
**裁定**：A。
**理由**：多跳题要求**实体链**可设计（角色兼任关系、跨文档因果），无答案题要求**缺失可控**（我明确知道全文没出现过「天数」）。公开语料这两点都靠运气；小说语料的无答案题会被「网上能查到」污染判官。
**代价**：写 28 篇文档是纯体力活，约 3 万字；规模只有「百级片段」，不是千级。
**被推翻的原因**（ADR-014）：自造语料让「文档事实」和「标准答案」同源，评测变成自证；真实论文的标签来自他人文本，且缺失可用 grep 证明而不是由我声明。规模问题也随之消失（14 篇 → 千级片段）。

## ADR-002 · 干扰靠相似条款，不靠语料规模
**问题**：100 多片段的语料，检索太容易，指标会虚高、改进不可见。
**选项**：A 把语料堆到上千片段 / B 在每篇里放措辞相近但阈值不同的条款。
**裁定**：B。
**理由**：真实系统的召回失败多来自「相似但不对」，而不是「库里没有」。四个套餐各写一遍退款条款、四个优先级各写一遍 SLA，top-8 里必然混入错误套餐的片段——这正是 rerank 与 RRF 该起作用的地方，也是指标有区分度的来源。
**代价**：`context_recall` 的绝对值会偏低（0.7 左右而非 0.9），不能跟别人的 0.95 横比。
**ADR-014 后的修订**：干扰源从「人工设计的相似条款」换成「真实论文的近邻表述」——三篇论文都报 `recall@k`、都定义 "faithfulness"、都给出 HotpotQA 上的数字，但口径与数值不同。原则不变（难度来自相似而非规模），只是干扰不再由我编造。

## ADR-003 · 砍掉联网兜底，改为显式拒答
**问题**：源仓库第 4 版有「本地不足 → 联网搜索」。
**选项**：A 不保留 / B 保留但默认关 / C 保留且默认开。
**裁定**：A。
**理由**：① 评测必须离线可复现，外部搜索结果每天都在变，接进来 `--baseline` diff 就失去意义；② 6 条无答案题会被联网结果直接答掉，`refusal_accuracy` 这个指标当场失效；③ 多一个外部 HTTP 依赖，与「零中间件可跑通」冲突。
**代价**：失去演示「兜底」的机会；源实现里 `evaluate` 节点的判充分性逻辑被放弃，只保留「不足就拒答」这个结论。

## ADR-004 · 行数预算：`app/` 600–800，`evals/` 单列
**问题**：「核心逻辑 600–800 行，不含 tests/data/docs」——`evals/` 三类都不属于，按最严读法 740+300=1040 直接破线。
**裁定**：核心逻辑只计 `app/` 包；`evals/` 单独预算 250–350 行，在 README 写明这是第二个预算。
**理由**：评测层是独立交付物（有自己的数据集、判官、门禁），把它压进 800 行只会导致判官逻辑被砍成玩具。两个预算各自可验证，比一个虚的单预算诚实。
**代价**：README 必须解释这个划分，否则外部读者会认为在钻空子。

## ADR-005 · 拒答用固定标记串 + 规则判定
**问题**：`refusal_accuracy` 用判官判还是规则判。
**选项**：A 判官 / B 规则 / C 规则优先、判官复核。
**裁定**：C。spec 强制拒答首句为固定标记串（ADR-014 后改为英文 `I cannot confirm this from the provided sources`），规则据此判定；判官只用于复核「标记存在但内容仍在编」的情况。
**理由**：判官判「是否拒答」是本末倒置——拒答是一个**格式**问题，不是语义品味问题。固定标记让判定零成本、零抖动、可单测；同时给用户一个稳定的信号词。
**代价**：回答措辞被约束，读起来略机械；如果模型忘了加标记，会被判成「没拒答」，可能低估真实能力。这是**故意选保守方向**（宁严不宽）。

## ADR-006 · 中文关键词侧用字符 bigram，不用 jieba — **SUPERSEDED by ADR-014**
**问题**：BM25 需要中文切分；`jieba` 是一个额外依赖。
**选项**：A jieba / B 字符 bigram / C 空格切分（中文不可行）。
**裁定**：B。
**理由**：① 省一个依赖，且 jieba 对 `ERR-4291`、`sk_live_`、`P1` 这类编号的切分不稳定；② 字符 bigram 对编号几乎是无损的（`ERR`、`RR-`、`R-4`…都有 n-gram 命中），而这正是向量侧的弱点、也是引入关键词侧的唯一理由；③ 无词典 = 无版本偏差，评测可完全复现。
**代价**：语义泛化弱于分词（「退款」与「退费」不同 n-gram，只能靠向量侧补）。README 必须写清这个取舍。
**被替换的原因**（ADR-014）：语料改为英文论文，中文切分问题不存在了。新规则：小写化 → 去标点 → 按空白切分 → 去停用词；**数字、`recall@k`、`HotpotQA` 这类词形原样保留**（这是 BM25 侧的真正价值：`4,409`、`18`、`ISREL` 这类字面量向量侧容易糊，关键词侧几乎必中）。

## ADR-007 · 融合用 RRF，不做分数归一化
**问题**：向量相似度（0–1 余弦）与 BM25 分数（无上界）量纲不同。
**选项**：A min-max 归一化后加权 / B RRF（按名次融合）/ C 只按 id 去重（源实现的做法）。
**裁定**：B。
**理由**：A 引入 `α` 这个超参，且 min-max 依赖当批结果的极值——同一文档在不同查询批次里分数不同，评测不可复现；C 等于丢掉一路（源实现 `merge` 的真实行为，见 source-audit D08）。RRF 只用名次，`k=60` 是文献默认值，不需要调参就能解释。
**代价**：RRF 丢弃了分数的「强度」信息（第 1 名和第 2 名都只差 1/61），在候选极度同质时排序不如调参好的加权融合。

## ADR-008 · 规划只做顺序推进 + 两道硬熔断
**问题**：`plan` 允许自拟查询或重拆子问题吗。
**裁定**：不允许。只能二选一；代码层强制 `rounds >= max_rounds` 或 `next_idx >= len(sub_questions)` 时生成。
**理由**：① 有界行为才可测——`test_loop_guard` 能写死「检索恰好 2 次」；② 自拟查询会让熔断条件失去参照（没有「还剩几条子问题」这个概念了）；③ 源实现（`rag-multihop.mjs`）的形态是顺序推进，缺陷在字段读错（D01）而不在模型选择空间，修正缺陷比扩大空间更值得。
**代价**：拆解质量决定上限——子问题拆得烂，plan 再聪明也救不回。写进已知限制。

## ADR-009 · 索引首次运行自动构建，不是独立脚本
**问题**：`pip install -e . && python -m app.cli` 必须直接跑通，但索引需要先建。
**选项**：A 单独 `--build-index` 步骤 / B CLI 检测索引缺失即自动构建 / C 每次运行都重建。
**裁定**：B，并保留 `--reindex` 强制重建。
**理由**：多一步就多一个「跑不通」的理由；`npz` 首次构建在百级语料下只需一次 embedding 批量调用（约数秒），缓存在 `.index/`，之后直接加载。C 会让每次提问都付 embedding 费用。
**代价**：首次运行有隐藏耗时，`--verbose` 必须提示「正在构建索引」。

## ADR-010 · 判官失败记 `null`，并用 `null_rate` 单独设闸
**问题**：判官返回无法解析时怎么办。
**选项**：A 当 0 分 / B 当 1 分 / C 跳过该条 / D 记 `null`，均值只算非空，另设 `null_rate` 闸。
**裁定**：D。
**理由**：A 会让「判官挂了」伪装成「模型变差」，方向错且不可诊断；B 更糟；C 会静默缩小样本量。D 把「能力」与「可靠性」拆成两个数字，门禁里 `null_rate > 10%` 直接 fail——判官不可信的评测结果不允许被当作通过。
**代价**：报告里出现 `null` 需要解释；`--limit 5` 这类小样本下 `null_rate` 波动大，故规定 `--limit` 下不执行门禁。

## ADR-011 · 保留 `fused` 与 `selected` 两个字段，而不是合并
**问题**：状态里 `candidates / fused / selected` 三个中间态是否冗余。
**裁定**：保留三层，且消费关系唯一：retrieve → candidates（去重）→ fuse → fused（RRF 排序）→ rerank → selected（≤top_n）→ answer。
**理由**：这三层分别对应三种可独立验证的失效——召回没拿到（candidates 空）、融合排错（fused 里没有正确片段）、截断截掉（selected 里没有）。合并成一层后，`test_empty_retrieval` 无法区分「没召回」和「召回了但被截断」。
**代价**：多两次数据搬运，约 15 行代码。

## ADR-012 · 把「能不能关掉」做成配置开关，用于消融
**问题**：项目要写进简历，最怕「混合检索效果更好」这句话没有数字支撑。逐个模块的增益怎么证明？
**选项**：A 不做，只报总分 / B 写四份独立代码版本对比 / C 用三个布尔开关控制，跑四次同一套评测。
**裁定**：C。`config.yaml` 里留三个开关：`retrieval.hybrid`（关掉只走向量）、`graph.multihop`（关掉时 decompose 退化为 `[question]`）、`rerank.enabled`。`evals.run --ablation` 依次跑四组并输出 diff 表。
**理由**：B 会产生四份会漂移的代码，一周后就无法确认它们除了开关之外是否还有别的差异；A 让整个评测层变成「一个孤零零的总分」，正好失去简历最需要的东西——**每一步的增量**。C 的代价只是三个 `if` 和约 40 行消融循环，换来一张「单路 0.xx → 加 BM25 0.xx → 加 RRF 0.xx → 加多跳 0.xx」的表。
**代价**：四组 × 30 条 × 3 判官 ≈ 360 次判官调用，一次全量消融的花费是单次评测的 4 倍。缓解：`--ablation` 支持配 `--limit`，先用 10 条看趋势；全量消融只在定稿时跑一次，结果进 `reports/`。
**风险**：开关组合会让「图」出现未测试的分支（如 `multihop=false` 时 `plan` 不该存在）。处理方式：`multihop=false` 时图编译成「route → retrieve → answer」三节点短路，不保留不可达的 `plan` 节点，且该组合纳入 `test_routing`。

## ADR-013 · 融合而非重建（统领性原则，优先于其他 ADR 的措辞）
**问题**：源仓库已有 5 个演进版本 + 5 个评测文件，能力是分散的。是"另写一个新项目"，还是"把 13 个文件融合成一个"？
**裁定**：**融合**。四条操作化规则，违反任何一条都算跑偏：
1. **结构可追溯**：每个目标模块必须对应明确的源文件（`plan.md §6.1` 的清单），不允许出现"来源不明"的模块。
2. **命名延续**：节点名与状态字段名沿用源实现与题目要求的交集（`route` / `decompose` / `retrieve` / `plan` / `answer`；`question` / `strategy` / `sub_questions` / `next_idx` / `rounds` / `candidates` / `fused` / `selected`）。不自创第二套词汇表——源仓库五个文件各用一套命名（`documents` / `retrievedDocs` / `esHits` / `merged` / `topDocuments`）已经是灾难，新项目不能再造第六套。
3. **能力逐条判定**：13 个文件里的毎一项能力必须归入「保留 / 合并 / 弃用（附理由）/ 新增」四类之一（`plan.md §6.0` 清单，18 项）。**不允许"没注意所以没做"**——弃用要写理由，合并要说清合并到哪个节点。
4. **署名口径改为"融合重构"**：README 写「在公开 Agentic RAG 实现基础上融合重构：5 个演进版本的编排合并为一张状态图，5 个评测文件合并为一套本地评测」。不再写「代码为独立重写」。

**与原始 Prompt 的冲突及处理**：原 Prompt 要求「不做逐行翻译、独立重写」。本裁定保留「不逐行翻译、不整段复制源代码」，但**取消"独立重写"的表述**——它与"融合"直接矛盾，且对简历不利：面试官追问「你这套图和市面上的 Agentic RAG 有什么不同」时，「改造并修正了一个有缺陷的实现」比「从零写了一个」更站得住，因为前者能讲出 15 个具体缺陷和修法。
**代价**：结构受源实现牵引，个别地方不如自由设计干净（例如 `decompose` 与 `plan` 的职责边界继承自源实现的重叠）。接受——这正是"融合"的意思。

## ADR-014 · 语料改用真实顶会论文全文，弃用自造手册
**问题**：原方案自造 28 篇虚构 SaaS「星轨工单系统」手册作为语料。问题不在工作量，在**可信度**：自造语料里的每个事实都是我自己写的，那么「检索到了什么」「答对了没有」这两件事就共享同一个作者，评测退化成自证。简历面试一旦被问「你的 ground truth 谁标的」，答案是「我自己写的文档和我自己出的题」，说服力归零。
**裁定**：语料改为 **14 篇 RAG 方向的顶会定版论文全文**（NeurIPS / ICLR / ACL / EMNLP / NAACL / TACL，用 arXiv 定版抓取），问题与参考答案从论文原文中提取，并用 `grep` 逐条验证。
**四项连带改动**（不改会自相矛盾）：
1. **语言**：语料英文 → 评测问题与参考答案必须英文。中文问英文语料会让 BM25 那一路变成随机数，`retrieval.hybrid` 的消融结论整块失效。ADR-006（中文用字符 bigram）随之作废，改为词级分词（小写 + 去标点 + 停用词）。
2. **拒答标记**：`无法从资料确认` 改为英文定串 `I cannot confirm this from the provided sources`。判定方式不变——首句前缀匹配（ADR-005 的规则优先原则保留）。
3. **无答案题**：从「我故意没写」升级为「论文里确实没写，且能证明没写」。每条无答案题在数据集里附 `absence_proof` 字段，记录验证用的 grep 命令，任何人可复核。这比自造语料硬得多——**可证伪**而不是**请相信我**。
4. **全文不入库**：arXiv 默认许可为「非独占授权」，不含再分发权。仓库只提交 `scripts/fetch_corpus.py` + `data/corpus.lock.json`（arXiv 编号 + 版本 + sha256 + 许可说明），全文进 `.gitignore`。抓取后文本哈希不符即报错——可复现性靠锁定，不靠拷贝。
**理由**：这个项目要写进简历，最贵的东西不是代码量，是「数字可被追问」。真实论文带来的三个好处：① 标签来自他人文本，不是我自证；② 论文互引构成天然多跳链（`Self-RAG` 评的是哪几个 benchmark → 那个 benchmark 的题目规模写在另一篇）；③ 同类方法、同类指标天然构成近邻干扰（三篇论文都报 recall@k，数值不同），不需要人工设计干扰项。
**代价**：① 检索难度上升，`context_recall ≥ 0.70` 可能达不到，阈值需在 T13 按真实基线重定，**不允许为了达标去改标注**；② 论文含大量公式与表格，抽取时已做处理（删 `<annotation>` 避免数字出现两遍、表格按行保留），仍有噪声，属可接受的「真实脏数据」；③ 需要联网抓一次（约 14 次 HTTP），之后完全离线。
**风险**：多跳链依赖论文间的真实引用关系，可能出现「两跳都在同一篇」的伪多跳。处理：标注时要求 `relevant_chunk_ids` 必须跨两个不同 `source` 文件，否则不计入 `multi_hop`，在 T04 逐条核。

## ADR-015 · 无 key 时用确定性哈希向量占位，且必须标注「指标不可用」
**问题**：`.env` 里是占位 base_url（`https://example.invalid/v1`）与假 key，真实 embedding 调不通。T05 要不要等 key？
**选项**：A 等 key 再写落盘逻辑 / B 用随机向量占位 / C 用确定性词袋哈希向量占位，并把「这不是语义向量」写进代码、配置与报告。
**裁定**：C。`config.yaml` 的 `index.embedder` 取 `hash | openai`；`HashEmbedder` 做 sqrt-tf + 符号哈希 + L2 归一化。
**理由**：B 最坏——随机向量下「索引写对没有」永远测不出来，怎么跑都像在工作，测试会变成 `assert True`。C 至少有真实的词面相似度：`4,409 question-answer pairs` 确实能召回 CRAG 摘要，说明切块、embedding 落盘、矩阵乘、top-k、RRF 这条链路是通的。但它没有同义与语序信息，所以**用 hash 跑出的 `context_recall` 不能写进任何结论**，`evals.run` 必须在报告头打印 embedder 名并在 hash 时给出显式警告。
**代价**：切到 `openai` 会触发一次全量重建（1357 片段，manifest 里 `embedder` 变了），且两次结果的指标不可横比——这正是 manifest 要记 embedder 的原因。

## ADR-016 · 行数口径改为「代码行」，并如实报物理行
**问题**：`app/` 物理 1156 行，超过 750 预算 54%。按原口径已经破线，但破线的部分主要是注释与空行。
**裁定**：对外同时报两个数：**代码行 732**（用 `tokenize` 排除注释、docstring、空行）与**物理行 1156**。预算按代码行考核，物理行照实写进 README。
**理由**：这个项目的价值一半在「为什么这么做」的注释里（每条都在指认源实现的具体缺陷），删注释能把物理行压到 800 以内，但那是把可读性换成数字，本末倒置。反过来只报代码行也不诚实——所以两个都写。
**代价**：README 要解释口径，否则读者拿 `wc -l` 一跑就发现对不上。超出预算的原因也照实写：`index.py` 274 行（原估 95）因为同时做了切块、两种 embedder、BM25 与 manifest 校验四件事。

## ADR-017 · `answer` 的拒答条件必须排除 simple 分支
**问题**：`answer` 用「召回为空」作为拒答条件。但 `route` 判 `simple` 时**本来就不检索**，候选恒为空——于是所有 simple 题都会被答成「I cannot confirm this from the provided sources」。
**选项**：A 让 simple 也走一次检索只为拿上下文 / B 在拒答条件里判断 `strategy != "simple"` / C 给 simple 单独一个节点。
**裁定**：B。
**理由**：这条是 T14 的 `test_simple_has_no_selected_but_still_answers` 抓出来的，不是设计时想到的——写测试之前，`--ask "What is 15% of 200?"` 会优雅地拒答，而评审看到的是一个"谨慎"的系统。A 违背 simple 分支存在的理由（省掉检索），C 让图多一个节点却没多一种能力。
**代价**：`strategy` 从"仅供观测"变成"参与控制流"，与 `next_action` 同属被条件读取的字段。已在代码注释里标明：改这个字段前先看 `answer` 的开头。

## ADR-018 · 每个事实只标「最直接的一片段」，摘要单独成块时补标
**问题**：论文里同一事实常出现 3–5 次（摘要、导语、实验设置、附录表）。全标则 `context_recall` 虚高且标注成本爆炸；只标一处则系统召回了「另一处等价表述」却被判错。
**选项**：A 标注全部等价片段 / B 只标最权威的一处 / C B + 摘要单独成块时补标。
**裁定**：C。
**理由**：A 会让 0.70 的阈值失去意义（随便召回一篇的任一段都算命中）；B 会造成**系统性假阴性**——摘要与导语几乎必然同批召回，只标导语等于人为压低指标。实测只有 `s01`（crag）与 `m10`（crag 被切块切断的续段）触发 C。
**代价**：`context_recall` 的绝对值偏低，**只能与同一份标注、同一 embedder 的结果横比**。README §6 已写明这条限制。

## ADR-019 · 消融基线用「拼接」而不是「单路向量」
**问题**：要证明 RRF 有用，基线该取什么？
**选项**：A 单路向量 / B 双路拼接去重（源实现的形态）/ C 双路按分数加权。
**裁定**：B 作为第二档，A 作为第一档。
**理由**：A 对比 B 回答的是「加关键词路有没有用」，B 对比 C 回答的是「融合有没有用」——两个问题不同，必须分开。C 被弃用是因为两路分数量纲不可比（余弦 0–1 vs BM25 无上界），任何加权系数都是拍脑袋。
**代价**：四组消融的模型调用量是单组的 4 倍，所以 `--ablation` 建议配 `--limit 10` 先看趋势。

## ADR-020 · `context_recall` 的分母看「标注」而不是「实际路由」，推翻早期「记 0」的裁定
**问题**：`route` 判 `simple` 的样本不检索，`selected` 恒为空。这些样本的 `context_recall` 怎么算？早期裁定是「记 0，并单列 `routing_accuracy`」。
**选项**：A 全部 30 条一律记 0 / B 排除「实际判成 simple」的样本 / C 排除「标注为 simple」的样本，但标注为 `complex` 而错判成 `simple` 的记 0 并留在分母。
**裁定**：C。数据集中 2 条 `simple` 题（`s13` RAG 全称、`s14` 15% of 200）的 `relevant_chunk_ids` 就是空列表。
**理由**：A 让 `context_recall` 同时惩罚「召回不准」和「正确地决定不检索」——后者是路由的功劳，不该扣召回的分，两个指标会测同一件事。B 更糟：模型把该检索的题错判成不检索，那条样本就被**排除出分母**，指标反而变好看，等于奖励偷懒。C 把「按标注定分母、按实际定分子」分开，误判只能让分数变差。
**代价**：分母是 28 而不是 30，报告的「参与 recall 条数」必须显式打印（已实现），否则读者会拿 28 条的分母去对比别人 30 条的分母。
